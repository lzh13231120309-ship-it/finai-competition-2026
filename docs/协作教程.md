# GitHub 四人协作教程（筹备版）

日期：2026 年 10 月 2 日。仓库尚未创建，本教程中的项目名是建议值；账号和范围确认后会更新为你们真实的仓库地址及操作记录。

## 1. 先理解四个词

仓库（Repository）：团队项目文件和历史版本的存放处。  
提交（Commit）：一次有说明的版本保存。  
分支（Branch）：个人修改的工作路线，让未完成的代码不影响主版本。  
合并请求（Pull Request / PR）：把分支修改交给同伴审查，再合入主版本。

Git 是本地版本管理工具；GitHub 是线上协作平台；GitHub Desktop 是方便新手操作的桌面客户端。GitHub 不会自动让网页上线，也不会自动同步未提交的文件，更不是四人同时编辑同一个 Word 文档的工具。

## 2. 推荐使用方式

先采用一个私有仓库，四人加入为协作者。免费个人账号支持私有仓库协作。对于四人新团队，这比先管理一个组织简单；代价是一个账号拥有仓库的最终管理权限，需要团队同意归属。

你们可以先约定：主分支 main 保持可运行；每个任务在自己的分支完成；至少一位同学检查 PR 后再合并。这是团队约定，只有实际配置并验证保护规则后，才能称为系统强制规则；不同套餐对私有仓库保护能力可能不同，不预先承诺免费账户能强制执行所有保护。

## 3. 创建和接入（尚待执行）

1. 四人分别注册并登录自己的 GitHub 账号，不共用密码。
2. 确认仓库归属，建议名称 finai-competition-2026，选择 Private。
3. 整理可分享的代码和文档，先配置 .gitignore，再检查文件清单。原有 data、密钥、数据库、日志、运行时、备份和大文件不整体上传。
4. 在本地保存首个版本，发布到确认的私有仓库。若走 GitHub Desktop 的 Publish repository，保留 Keep this code private 勾选；若网页上新建空仓库与已有本地历史连接，不重复初始化 README 造成两套历史。
5. 所有者打开仓库 Settings → Collaborators → Add people，按同学的准确用户名邀请。同学接受后才获得访问权限。
6. 其余三人在 GitHub Desktop 登录各自账号，通过 File → Clone repository 选择这个仓库，保存到自己的电脑。
7. 验证四人看到同一仓库和最新 README。不要把本地复制路径或 localhost 当成团队共享网址。

本机目前尚未检测到默认位置的 GitHub Desktop。安装应从官方地址获取；是否改用其他方式待账号与授权情况确认。浏览器登录和授权由账号本人操作，不在聊天中发送密码、验证码或访问令牌。

## 4. 每天工作的固定步骤

### 开始前：同步并认领任务

打开 GitHub Desktop，选择团队仓库。切到 main，点击 Fetch origin；若显示 Pull origin，再点击拉取。同学需要先把自己的未完成修改提交到分支，再切换，避免误混修改。

在 GitHub 网页 Issues 查看任务，指定负责人，写清“要做什么、输入输出、怎么算完成”。一个 Issue 对应一个可验收的小任务，例如“提取一份公告中的质押数量并保留页码”，而不是“完成全部 AI”。

### 开发时：建立自己的分支

在 Current branch → New branch 创建分支。例如 feature/extraction-pages、feature/financial-ratios、feature/valuation、feature/frontend。确认基于最新 main 创建，然后修改文件。

不要四个人直接向 main 上传不同的压缩包。尽量不要多人同时修改同一文件；统一接口变更要先在 Issue 中说明。

### 保存时：检查改了什么

在 Changes 查看每个文件的变化。看到密钥、data、数据库、大量内置依赖或个人文件，先停下修正上传清单。只勾选本次任务需要的文件。

填写 Summary，例如“提取公告质押数量并记录来源页码”，在 Description 说明验证样例和限制，然后 Commit to 当前分支。提交只保存在本机；Publish branch 或 Push origin 才把这个版本上传到 GitHub。

### 交付时：申请同伴检查

点击 Create Pull Request 或 Preview Pull Request，确认 base 为 main，compare 为自己的分支。说明变化原因、使用示例和验证结果，邀请另一位同学检查。

审查者查看 Files changed，提出意见或认可。作者改完后继续提交并推送同一个分支，PR 会自动更新。确认可运行、计算可核验、没有密钥后再合并。

### 合并后：全员更新

所有人切回 main，Fetch origin、Pull origin，再开始下个分支。已有长期分支要按需合并最新 main；若出现冲突，先保留备份再解决，不乱选“全部接受”。

## 5. 一次低风险练习

仓库接通后，每人在独立分支添加一份 docs/team/自己的用户名.md，写主责方向和可工作的时间，不写身份证、学号照片等私人材料。提交、推送、创建 PR，由另一人审查，再合并。四人练习文件互不重叠，可先熟悉流程。

练习真正完成的标准：其他同学拉取后能看到该文件，网页显示版本和 PR，主分支仍可用。

## 6. 如何安排任务

建议 Issues 任务包含：目标、负责人、所用材料、预期输出、验收方式、依赖、截止日期。若启用 Projects，看板可以设“待做、进行中、待检查、已完成”；Projects 是独立功能，需要实际建立，本轮尚未建立。

先安排这些任务：确认第 5 / 6 项；统一数据结构和来源字段；选择一个公告和一份财报样例；制作少量人工核验答案；打通提取—分析—估值；制作最小展示；准备计划书及视频。

## 7. 常见问题

**同学看不到私有仓库**：确认用户名、邀请是否接受，以及 Desktop 登录的是哪个账号。

**提交后同学仍看不到文件**：检查是否 Push origin，以及是否只在个人分支、尚未合并 main。

**网页有更新，本机没有**：Fetch origin 后按需 Pull origin。若提示本地有未提交修改，先保存到自己的分支，不丢弃修改。

**冲突**：两人改了同一段内容。先备份，逐段判断保留什么，运行相关检查，再提交解决结果；不通过删除整个文件解决。

**误删文件**：先停止继续覆盖，从 History 查看历史差异；由熟悉操作的人在新分支恢复文件或撤销指定提交。共享分支优先新增恢复提交，不强行重写大家的历史。

**误上传密钥**：立即撤销或更换泄露密钥，并通知仓库负责人处理历史。删除最新文件不能消除历史中的密钥，私有仓库也不能代替密钥管理。

**软件运行不了**：GitHub 只共享被提交的文件。各自电脑仍需按项目运行说明配置依赖和自己的模型授权；不靠上传整套 runtime 和个人 data 来代替可复现安装。

## 8. 备份与知情权

本项目后续每次修改都应说明修改理由、影响范围、检查结果和限制，保存修改前副本及修改后快照。未提交的修改要备份；源码提交要有可读说明；阶段成果要标记版本。备份文件夹不放入共享仓库，避免体积膨胀或把私人信息重新上传。

要重新生成时，保留旧版本并创建新版本，说明替换原因。恢复操作先备份当前状态，不直接覆盖四人的修改。
